# Rusty Rival v1.0.79 — Chess960

Qualified on 2026-10-19 (qualification run 9, source `c94d78d`). Production remains v1.0.78 until the public release asset passes its own checks and the bot is switched during an idle window (see Lichess bot below).

## Change

NET-1762: the engine plays Chess960 (Fischer Random), so the Lichess bot can accept and issue `chess960` challenges. For standard chess the measured search output is identical to v1.0.78. The move encoding and move generation order are unchanged; fixed-node, held-out and bench results match v1.0.78 exactly (default bench 2,958,774 nodes; 16-position depth-16 bench 14,935,871 nodes; see Evidence). The one deliberate change on the standard path is the flag-first `verify_move` correction described below, which changes none of those results.

What changed:

* Each colour's castling rook squares live in `Pieces` (`castle_rook_squares`, the standard corners unless the FEN says otherwise), in padding the struct already had, and `Position::castling_960` (also in existing padding) records whether any right needs the general form: a king off e1/e8 or a rook off its corner. Neither struct grows (checked at compile time). The castling-sensitive code (make/unmake, castle generation, `verify_move`, and the search and quiescence functions that inline them) is compiled twice over a `C960` const generic, and `iterative_deepening` picks the form once per search from the root position's flag, which every position in the game shares and which depends only on the board, never on the `UCI_Chess960` option. The orthodox form is the v1.0.78 code, constant squares, masks and Zobrist deltas included, apart from the flag-first `verify_move` correction and the inlining attributes below, with no Chess960 branch or call left in it; the general form runs only for Chess960 geometry. Code outside the search (perft dispatches once too; UCI legality, datagen move filtering and tests call wrappers) dispatches on the flag. The squares never change during a game; a right whose rook has left its square is cleared exactly as before.
* Speed gate: a paired matched-PGO throughput test, 20 blocks of `bench depth 16` on one thread with a fresh process per run, against a fresh PGO build of the v1.0.78 source made in the same window. The rule began as strict zero margin (95% lower bound of the paired log-ratio ≥ 0; speed-decision-1). On 2026-10-18 Chris set the tolerance to 0.25% ("0.25% is tolerable", speed-decision-2), so the lower bound must be ≥ −0.25%. Runs 2 and 3 were judged under the strict rule and are recorded as such.
  * Run 2, `43f6ad2` (general form everywhere): −0.91% [−1.04, −0.78]; rejected.
  * Run 3, `d48cbc8` (orthodox fast paths behind a runtime `castling_960` test): −0.54% [−0.78, −0.29]; rejected (it would also fail at 0.25%). Disassembly showed the never-taken tests left 50 out-of-line Chess960 call sites, with their spills, inside `search` (+810 instructions) and 9 in `quiesce`. The compiled-twice design removes them from the orthodox form altogether.
  * Run 4, `d2db029`: stopped in the test suite (the `verify_move` defect below); no speed measured.
  * Run 5, `b69e8ed`: stopped in the PGO driver's profile check (below); no speed measured.
  * Run 6, `7ddb9a6`: stopped at the structural screen (inlined wrappers, below); no speed measured.
  * Run 7, `fb051d1`: −1.34% [−1.55, −1.13] at the 0.25% margin; rejected. The orthodox quiescence search called `quiesce_moves_into` out of line (below).
  * Run 8, `c94d78d`: −0.59% [−1.23, +0.06] at the 0.25% margin; inconclusive, not accepted. Block-to-block spread was about three times run 7's and the host was loaded. Chris chose "fix first" before run 8 and "Quiet-machine re-test" after it.
  * Run 9, `c94d78d` unchanged: +0.10% [−0.15, +0.36] at the 0.25% margin; passed, all 20 blocks kept. A host-quietness guard ran: 120 s settling, load ≤ 1.50 at admission (measured 1.01) and ≤ 2.50 throughout (maximum 2.06), 538 one-second samples, all accepted.
  This shows no slowdown beyond the 0.25% tolerance in one quiet window on this host. It is not a speed-up claim and not a guarantee for other hosts or builds.
* PGO: the profile is trained on standard chess, so only the orthodox form is profiled; the Chess960 form ships unprofiled. Chess960 play is not speed-gated, and the Chess960 smoke and oracle checks run against the PGO release binary, so the shipped Chess960 code is the code tested. `scripts/build_pgo.py` checks that the profile has positive counts for the hot engine functions; it now names the orthodox instantiations `search_c960::<false>` and `quiesce_c960::<false>` (v0 symbols `…search_c960Kb0_E…`, anchored to the function itself, not closures inside it), because the non-generic `search`/`quiesce` are dispatch wrappers the release binary never calls. Qualification run 5 (`b69e8ed`) stopped on that check after the 330/0/3 suite and a profile that had trained the orthodox form (search 4,452 counters, maximum block count 2.67 billion); engine source is unchanged.
* The fourteen public dispatch wrappers (`make_move`, `make_move_in_place`, `unmake_move`, `verify_move`, `generate_moves`, `generate_quiet_moves_into`, `make_move_nnue`, `unmake_move_nnue`, `iterative_deepening`, `start_search`, `search`, `is_draw`, `quiesce`, `perft`) are `#[inline(never)]`, so every entry into Chess960 code from outside the general form goes through one of them and the binary keeps those boundaries after optimisation. Qualification run 6 (`7ddb9a6`, where they were `#[inline]` or unannotated) stopped at the structural screen because UCI and datagen callers had absorbed inlined wrapper copies and called Chess960 helpers directly; none of those callers is reachable from the orthodox search, which calls only the specialised forms. That run's suite, PGO build and oracle passed and no speed was measured. Only these attributes changed; the specialised bodies are untouched, and the extra call costs one per UCI command or datagen move.
* `quiesce_moves_into` and `decay_history_tables` are `#[inline(always)]`. In v1.0.78 each had one live caller and was inlined into it. Compiling the search twice gave each a second caller (the Chess960 form), and the optimiser then kept them out of line. Qualification run 7 (`fb051d1`) passed every functional gate and the structural screen but measured −1.34% in standard-chess speed; its binary called `quiesce_moves_into` out of line from the orthodox quiescence search, a call v1.0.78 does not make. The attribute restores the v1.0.78 compiled shape. Bodies and behaviour are unchanged.
* FEN castling field: `KQkq` (X-FEN, the outermost rook on that side of the king), Shredder-FEN rook files (`HAha`, what lichess-bot and python-chess send for Chess960), or a mix. `get_fen` writes `KQkq` for a rook on its corner and the file letter otherwise, so the engine's own FEN round-trips with the same castling rook. A file letter that names no rook grants no right; `K`/`Q` with nothing behind them are still recorded as written (NET-369 behaviour kept).
* Castling is generated in general form: the king lands on the g or c file and the rook on f or d from wherever they start; every square the king or rook crosses or lands on must be empty apart from the two pieces, and the king may not start on or cross an attacked square. The king may move one square or none and the rook may already stand on its destination. In the standard start this is exactly the old f1/g1 and b1/c1/d1 test.
* `verify_move` recognises a castle by its flag, never by distance, in both compiled forms, so a one-square Chess960 castle cannot be mistaken for a plain king step even when it is presented to a position compiled in the orthodox form (the same board with its rights gone). An earlier specialised candidate (`d2db029`) kept the v1.0.78 king-step-first order in the orthodox form and failed `verify_move_tells_a_one_square_castle_from_a_king_step` in qualification run 4, in the release test binaries and before the PGO build, identity, oracle, structural screen or speed measurement; the flag test costs one AND on king-move verification and adds no Chess960 call.
* UCI: `option name UCI_Chess960 type check default false`. python-chess refuses to run a Chess960 game against an engine that does not advertise it. With the option on, castles are written as the king taking its own rook (`e1h1`) in `bestmove`, `ponder` and the PV; `position … moves` accepts that spelling always, and the standard `e1g1` spelling whenever it is unambiguous (a king double-step), with the option on or off.
* The transposition-table lock includes the castling rook of each active right whose rook is not on its standard corner (a compile-time SplitMix64 salt, zero for the corners), so Chess960 positions that differ only in which rook a right refers to (`KQ` outer rooks versus `GB` inner rooks) no longer share a key. Every standard-chess key is unchanged.
* A castle whose king moves fewer than two squares is written king-takes-rook even with `UCI_Chess960` off, because its from/to spelling (`b1c1`, `g1g1`) would read back as a king step or not at all. Standard castles always move the king two squares and keep their `e1g1` spelling.
* `invert_fen` swaps the case of rook-file castling letters too.

Not changed: evaluation (the NNUE net has no castling-rights input), time management, pondering, Syzygy probing (still only with no castling rights), bench and datagen.

## Evidence

* Perft: 12 Chess960 positions (including the standard start spelled `HAha`) and 10 hand-built castling geometries (king does not move; rook does not move; one-square castle beside the king step; blocked rook path; attacked king path; the Chess960 case where the castling rook shields the king from a queen on a1 until it moves; X-FEN versus Shredder-FEN; long king walk) agree with Stockfish 17 `UCI_Chess960` perft at depths 1–4 (`tests/chess960.rs`). Depth-4 totals range 3,507 to 1,171,749 nodes.
* Make/unmake, copy-make versus in-place make, incremental Zobrist and pawn keys against from-scratch recomputation, and FEN round trips through every move of those positions one ply deep.
* NNUE incremental accumulator equals a full recompute through Chess960 castles (the castle delta reaches the fused `(2,2)`, `(1,1)` and generic paths).
* `scripts/chess960_uci_smoke.py` (python-chess 1.11.2, lichess-bot's driver): 30/30 checks — option advertised and managed by python-chess, both castle spellings on `position`, `bestmove` spelling with the option on and off, clocked `go` within budget, `go ponder`/`ponderhit`, 15 Chess960 self-play games of 40 plies with every move legal (11 castles) plus a standard game and a resumed game after king-takes-rook castles.
* Existing suite: all previous tests pass; `castling_is_not_generated_without_the_pieces` now also pins the Chess960 reading of a king away from e1 with `KQ` rights (castles d1g1/d1c1), the `verify_move` reference carries the castle-flag split, and `position_applies_en_passant_and_promotions_through_is_legal_move` pins en passant and promotions through the move-based `is_legal_move`. `both_search_forms_agree_on_orthodox_positions` runs the two compiled search forms on orthodox positions at depth 7 and requires the same move after exactly the same node count. `cargo test --release --workspace`: 330 passed, 0 failed, 3 ignored in qualification run 9 (v1.0.78: 311/3).
* Standard-chess identity, qualification run 9 (source `c94d78d`; PGO release build SHA-256 `d8aafb8b797a04f0732a06ff0d870c30037b33c0749106194e0c5dbf86301f2e`). 80 fixed-node positions at 100k nodes are identical line for line, 80/80, in each of three pairs: against its own non-PGO build, the public v1.0.78 Linux AVX2 asset (SHA-256 `d45e0a8fad0bbe10f073b75e7405d0644ca6a576bceae262f434f14ba5407954`) and its own portable x86-64-v2 build. 60 held-out positions at depth 16 give exact identity, 81,838,789 nodes, in the same three pairs. Bench 2,958,774 nodes and the depth-16 bench signature of 14,935,871 nodes equal v1.0.78's. The Chess960 smoke passed 30/30 against the PGO binary (`id name Rusty Rival 1.0.79`), the clocked smoke 5/5, the move oracle 6,300 rows, and the bounded structural screen passed. That screen checks the orthodox search, quiescence and iterative-deepening functions and their crate-local closure. It requires no direct, immutable-GOT or address reference into Chess960 code, wrappers that keep their boundaries, code-growth caps against v1.0.78, the absence of the two inlined helpers, and quiescence callee parity. Register-indirect transfers it cannot resolve are listed and excluded, so it is not a whole-program reachability proof. ## Limitations

* No Chess960 strength claim: measured standard-chess search output is identical to v1.0.78, and Chess960 play has only been smoke-tested, not measured against another engine.
* The HCE fallback (`UseNNUE false`) keeps its standard-geometry king-safety terms; it is not used in play.
* A GUI that plays Chess960 without `UCI_Chess960` must send king-takes-rook for a castle in which the king moves one square or none; the engine writes such castles that way in both modes.
