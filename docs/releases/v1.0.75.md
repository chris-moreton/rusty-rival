# Rusty Rival v1.0.75

A raw-speed release that reuses quiescence-search buffers and shares exact NNUE update kernels.

## Changes

- Reuse per-ply move and move-score buffers in quiescence search, with independent ownership per search thread and fresh pools on clone.
- Share the existing NNUE feature-update kernels between perspectives instead of duplicating their machine code. Wrapping integer arithmetic and feature order are unchanged.

The network, evaluation scale, pruning parameters, move ordering, tablebase behavior and UCI settings remain unchanged. The additional quiescence buffers allocate lazily: retaining both buffers at all 256 plies would add about 0.8 MiB per search thread, plus slot metadata and allocator overhead.

## Measured scope

On one Ryzen 9 5950X, Linux x86-64-v3, fresh matched PGO builds, one thread and Hash 128:

| Workload | Build pair 1 | Build pair 2 |
| --- | ---: | ---: |
| Bench depth 20 | +1.34% | +1.26% |
| 60 positions at depth 16 | +1.56% | +1.42% |

Each comparison used four paired timing blocks. Both independently rebuilt pairs met the frozen acceptance threshold; they are not pooled. A depth-18 diagnostic on pair 2 measured +1.41%. Same-source PGO rebuild controls measured -0.08% on bench and -0.10% on the 60-position workload, with intervals spanning zero; results were not adjusted by these controls. Timing intervals describe within-pair measurements, not variation across machines. The combined change was measured directly; component gains are not added or attributed to an interaction.

## Correctness evidence

The research candidate passed 289 release tests (three existing ignored tests, no exclusions), 24 debug library tests, both five-test buffer lifecycle suites, 17 Python tests and CI-style checks. Both PGO pairs matched on 80 fixed-node and 60 fixed-depth positions, including nodes, scores, PVs and best moves. Scalar x86-64-v2 builds matched on the same 140 positions and matched the AVX2 candidate. The 80 fixed-node positions are PGO training positions; the 60-position workload is disjoint from those and bench roots, but was reused from earlier speed research.

These are same-host, single-thread raw-speed results, not an Elo, multi-thread or cross-platform speed claim. A faster time-limited search can naturally choose a different move because it searches more nodes. Windows, macOS and aarch64 performance was not measured in this research.
